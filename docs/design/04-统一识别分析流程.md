# 统一识别分析流程设计

> 把"识别（OCR/抽取）"与"分析（对齐/比价）"用同一个**锚点键**串成一条流水线。
> 设计参考：fabric-bridge 的"分类→按类抽取→锚点归一"架构 + 2025–2026 业界文档智能处理最佳实践。
> 背景动机见 §1，最小落地切片见 §8。

## 1. 背景与问题

### 1.1 现状的两个症状

1. **supplier_name 被品牌污染**：封面公司名识别不到，明细表"品牌"列里的 KITZ / 伯尔梅特 被当成供应商名。
2. **三家供应商对不齐**：同一个标，凯硕新正报价条数 ≈ 泰科龙的两倍，系统对齐准确率天然受限。

### 1.2 根因：在做"两两配对"，且没有锚点

当前对齐逻辑是把多家供应商报价**两两语义匹配**（猜"A 的第 12 条 = B 的第 8 条"）。这正是实体消解领域明确警告要避免的 n² 配对问题，而且我们连一个公共基准都没有。等于让人不看招标题目、只拿三份答卷去倒推题目——勉强能做，但准确率有天花板。

### 1.3 fabric-bridge 的关键启示

fabric-bridge（同样用 DashScope Qwen VL 的 OCR 流水线）**从不做文档两两配对**。它的架构是：

```
每页先分类（制造指示書 / 別注品詳細 / 仕様書）
  → 按类型用专属 prompt 抽取
  → 抽取时归一到一个共享锚点键（hinban 款号 / 5位订单号）
  → 两份文件靠锚点键互相交叉校验、互相补字段
  → "分析"= 对锚点键做 GROUP BY（CAD 报表 = fabric_model+color_code 聚合）
```

两份订单文件是同一批货的**两个视图**，靠 hinban 互校，而不是互相配对。最终报表只是聚合。

### 1.4 业界最佳实践印证（2025–2026）

| 实践 | 来源结论 | 对本系统的含义 |
|------|---------|--------------|
| 分类是单点故障 | 文档类型分错 → 用错 schema → 整段抽取作废 | 必须做页级角色分类，且优先保证它的可靠性 |
| 纯抽取与后处理分离 | 只抽"看得见的"，业务推断单独做，可显著降幻觉 | 抽取阶段不做品类推断/品牌排除 |
| OCR 文本 + 图像一起喂最好 | 文本给内容，图像给版面 | 关键字段兜底时回到原图 |
| schema-first 实体消解 | 先有 schema（锚点）再匹配，嵌入分块取代字符串规则 | 锚点优先，而非两两配对 |
| 校验失败 → 带结构化错误进人工 | 保留 best-effort 作为复核起点，不静默丢弃 | 对不上的行进复核队列 |

## 2. 设计原则

1. **锚点归一，不做两两配对**：先确立锚点（招标清单行，或规范键聚类），各供应商各自落位。
2. **分类先行**：每页先判角色，再决定抽取与去向。封面/投标函负责元数据（供应商名、总价），报价清单页负责明细。
3. **纯抽取与后处理分离**：抽取只输出页面上可见的内容；品类推断、品牌排除、归一化在独立后处理层做。
4. **成本分层**：便宜模型（OCR + 文本 LLM）扛全量，贵的通用 VL 只在**校验失败**时介入。
5. **校验和驱动重读**：用"Σ明细 == 投标总价"作为抽取完整性的校验和；不通过才触发 VL 重读。
6. **人工兜底而非静默丢弃**：校验/对齐失败的条目带原因进复核队列。

## 4. 各阶段详述（含模型选型）

### ① 页级角色分类

**目的**：把每页归到一个稳定角色。角色由**招标流程**决定（封面/投标函/资质/技规/报价清单），跨供应商稳定——这是能从 fabric-bridge 抄过来的部分。

**为什么不需要多模态分类模型**：每页已经跑过 qwen-vl-ocr 拿到 HTML，分类直接在这段文本上做。我们需要的区分很粗：

- **报价清单页**：HTML 含表格，且表头出现"单价/数量/规格/合价"等列 → 走明细抽取
- **非清单页**：无表格或表格稀疏 → 走元数据抽取（封面/投标函取供应商名、总价）

**模型选型**：
- 主路：**规则判断**（HTML 有没有含价格列的表格）→ 几乎零成本、可靠
- 边界情况：**qwen3.6-flash（文本）** 在 OCR 文本上分类，参考 fabric-bridge 的 `CLASSIFY_PAGE`
- 仅当封面 OCR 文本过稀疏（大标题图、表格解析为空）：退到 **qwen3-vl-flash 看图**

> 不使用 qwen-vl-max 做分类——视觉推理能力过剩、成本高，本场景用不上。

### ② 按角色抽取

**报价清单页**：维持现有两段式 `qwen-vl-ocr (table_parsing) → qwen3.6-flash 结构化`。

**非清单页（封面/投标函）**：抽取 supplier_name 与**投标总价**。供应商名在封面/投标函的固定位置（"投标人："、"投标单位名称："），不再跟品牌列抢。投标总价作为 ④ 的校验和输入。

**纯抽取原则**：本阶段只输出可见内容；`_infer_category`、品牌排除等推断逻辑移到独立后处理层。

### ③ 归一到规范键

为每个品类定义**规范键（canonical key）**，抽取的职责是把每行填成这个键。以阀门为例：

```
规范键 = (阀门类型, 公称直径DN, 公称压力PN, 连接方式, 阀体材质)
例：(蝶阀, DN100, PN16, 对夹, 球墨铸铁)
```

规范键是后续对齐的锚点单元。颗粒度差异（凯硕按单台列、泰科龙按规格汇总）在归一后落到同一个规范键上，1:N 关系自然合并。

### ④ 校验体系（见 §6 展开）

单页算术校验 + 多页总价校验和。**校验和不通过 → 触发 ⑥ 重读**。

### ⑤ 锚点对齐（见 §5 展开）

有招标清单用清单做锚点；无清单对规范键做语义聚类生成锚点。**替代两两配对**。

### ⑥ VL 重读兜底

**触发条件**：④ 校验失败（Σ明细 ≠ 总价，或关键字段缺失）。

**模型选型**：**qwen3-vl-flash（通用 VL）读原图**，不是 qwen-vl-ocr。原因：校验失败通常是 table_parsing 把表结构搞乱了（合并单元格、盖章遮挡致行错位），换一个"看图推理"的通用 VL 读原图能救回来。

**范围**：只对失败的那一页/那个区域重读，不是全量重读——大多数页通过校验，成本可控。这正是 fabric-bridge Stage 3（裁盖章区用 qwen3-vl-flash 重读 process_type）的套路。

## 5. 锚点对齐策略

### 5.1 有招标清单（主流程）

招标清单的每一行是一个锚点行。每家供应商的每条明细，归一成规范键后 match 到对应锚点行。

```
招标清单行（锚点，纵轴）
   × 供应商（横轴）
   = 比价矩阵，每格填入该供应商在该锚点行的报价
```

这是 schema-first 实体消解：招标清单 = schema/blocking key。

### 5.2 无招标清单（降级流程）

没有清单时，**合成锚点**：

1. 把所有供应商的明细归一成规范键
2. 对规范键做语义聚类（嵌入分块），每个簇 = 一个锚点行
3. 各供应商落位到锚点行

明确告知用户"当前为估算对齐，建议导入招标清单后重对齐"。

### 5.3 为什么这样能解决"对不齐"

不再两两配对，先有锚点再落位。颗粒度不同不影响——多条明细落到同一锚点行就是同一格（带数量合并）。对齐率从"猜对的比例"变成"能落到锚点的比例"，可度量、可优化。

## 6. 校验体系

### 6.1 单页校验（纯代码，无 LLM，每页）

| 校验 | 规则 |
|------|------|
| 数值强转 | qty / unit_price / total_price → float（复用 `_coerce_num`） |
| 行算术 | 合价 == 单价 × 数量（容差内）；不符标记 |
| 噪声行过滤 | 丢表头、合计、小计行 |
| Schema 校验 | Pydantic；失败带结构化错误进复核 |

### 6.2 多页校验和（纯代码，每供应商）⭐

```
Σ(本供应商所有明细合价) == 封面/投标函标注的投标总价 ?
  ├─ 相等（容差内）→ 抽取完整，放行
  └─ 不等          → 漏行/重复/识别错，触发 ⑥ VL 重读 + 标记复核
```

这是整套流程**信息量最大的单一校验**：投标总价就是明细抽取的校验和。对应 fabric-bridge 的 `total_qty == sum(sizes)`。

### 6.3 跨文档校验（可选，高价值）

| 视图 | 用途 |
|------|------|
| 投标文件 vs 问询函（二次报价） | 同条目不同价，核对调整逻辑 |
| vs 招标结果审批表 P5-P6 | 人工比价真值，做最终对账与评估基线 |

## 7. 模型选型与成本分层

| 阶段 | 模型 | 类型 | 触发频率 |
|------|------|------|---------|
| 表格 OCR | qwen-vl-ocr (table_parsing) | 专用 OCR | 每页 |
| 结构化抽取 | qwen3.6-flash | 文本 LLM | 每个清单页 |
| 页面分类 | 规则 +（边界）qwen3.6-flash | 规则/文本 | 每页 |
| 单页校验 | — | 纯代码 | 每页 |
| 多页校验和 | — | 纯代码 | 每供应商 |
| 规范键归一 | qwen3.6-flash 或规则 | 文本/规则 | 每明细行 |
| 无清单锚点聚类 | 嵌入模型（text-embedding） | 嵌入 | 仅无清单时 |
| **VL 重读兜底** | **qwen3-vl-flash** | **通用 VL（看图）** | **仅校验失败页** |
| 封面取名兜底 | qwen3-vl-flash / 文本 | VL / 文本 | supplier_name 为空时 |

**原则**：贵的通用 VL 只碰失败样本；全量走便宜的 OCR + 文本模型。

## 8. 与现有代码的差距 / 最小落地切片

fabric-bridge 是单客户固定格式，才敢硬编码 per-type prompt；我们面对任意供应商格式，**抄不了那部分**。能抄的是"分类→按类抽取→锚点归一"的骨架。守住"不要过度设计"，**高 ROI 最小切片只有三块**：

| 切片 | 解决 | 现状差距 | ROI |
|------|------|---------|-----|
| **页级角色分类** | supplier_name + 过滤噪声页 | 现仅文件级 doc_type（用户手选），无页级分类 | 高 |
| **规范键先行** | 对齐前提 | 现抽取不产出规范键 | 高 |
| **锚点对齐替代两两配对** | 三家对齐 | 现为供应商间两两匹配 | 高 |

已完成的相关改动：
- ✅ 多 Key 轮转 + 429 退避重试（`dashscope_ocr.py`）
- ✅ `_pick_supplier_name` 品牌排除 + 封面取名兜底（`aggregator.py` / `pipeline.py`）

暂不做（ROI 低或依赖数据）：跨文档校验、无清单语义聚类的精细调优、26SWP 式多格式分类器。

## 9. 衡量指标

| 指标 | 定义 | 目标 |
|------|------|------|
| 总价校验和通过率 | Σ明细 == 投标总价 的供应商占比 | 抽取完整性主指标 |
| 锚点落位率 | 能 match 到锚点行的明细占比 | 对齐主指标 |
| supplier_name 准确率 | 取到正确公司名（非品牌/非空）占比 | — |
| VL 重读触发率 | 触发兜底的页占比 | 越低越好（成本） |
| 人工复核条目数 | 进复核队列的行数 | 越低越好 |

## 10. 待确认 / 开放问题

1. **招标清单来源**：这批阀门标的标准条目，是否有结构化的招标清单可作锚点？（`docs/项目资料/初始资料/` 待核）
2. **规范键字段**：阀门规范键的字段集需与业务确认（是否含驱动方式、法兰标准等）。
3. **总价位置**：投标总价在封面还是投标函固定位置？多轮报价以哪一版为准？
4. **审批表真值**：`招标结果审批表` P5-P6 的横向对比表能否作为对齐评估基线导入？
