# 招标比价 E2E 后端独立审计与整改建议

> 审计日期：2026-06-22  
> 范围：招标清单确认、报价确认、对齐、矩阵、评标解释、导出、历史价格与邀标供应商召回。  
> 性质：只读代码审计；本报告未修改生产逻辑、数据库或 match 结果。

## 1. 审计方法

本次没有沿用 Claude 的结论作为前提，而是从真实调用路径反向核查：

1. 路由入口与前端实际调用；
2. session / submission / supplier 身份解析；
3. 报价确认到 `BidQuoteLine` 的持久化；
4. anchor match、review matrix、bid matrix、export；
5. 评标政策、AI insight 与历史价格服务；
6. 测试覆盖与未覆盖分支。

同时按官方 Claude Code 最佳实践复核仓库规则文件。官方建议 `CLAUDE.md` 简洁、具体、结构化，目标控制在约 200 行以内；按代码域变化的要求使用 `.claude/rules/` 路径规则，而不是把所有历史决策持续堆入根文件。

参考：

- <https://code.claude.com/docs/en/memory>
- <https://code.claude.com/docs/en/best-practices>

## 2. 总体结论

当前主 E2E 已具备可运行骨架，但后端仍处于“新 submission 主路径 + 旧 supplier/alignment 兼容路径 + 路由内大量编排”并存状态。

最需要警惕的不是文件太长本身，而是以下三类业务风险：

1. **旧路径仍可达且存在确定性运行时错误**；
2. **评标、历史价格和邀标证据口径没有完全收敛到权威服务**；
3. **submission 身份、审计证据和迁移机制仍有半迁移状态**。

目录拆分应该服务于这些边界，而不是为“文件整洁”进行大重构。建议先修 P0 行为，再做服务拆分。

## 3. P0 发现

### P0-1 旧矩阵路径存在确定性 `NameError`

位置：`apps/api/services/bid_matrix.py:369`

`_build_alignment_row()` 局部变量是 `first_data`，返回值却引用不存在的 `first_qt.material_id`。该分支一旦处理 confirmed alignment group 会直接失败。

这不是死代码：`build_bid_matrix()` 仍被 `analysis.py` 和 `export.py` 的兼容路径调用。当前测试通过不能证明该分支安全，因为现有 71 个相关测试没有命中这个具体分支。

建议：

- 若旧矩阵已无业务价值，明确下线入口并删除；
- 若需兼容，立即修复变量并增加“存在 confirmed alignment group”的回归测试；
- 禁止继续让新旧矩阵在生产中无标识共存。

### P0-2 评标政策把未知项目错误标成已知政策

位置：`apps/api/services/evaluation_policy.py:39-44,81-87`

`get_evaluation_policy(project_id)` 完全忽略 `project_id`，所有项目都返回：

- `reasonable_low_price`
- `single_supplier`
- 固定八项因素
- committee decision

“不自动定标”是保守的，但宣称招标文件采用合理低价法、单一授标仍然是在补造政策事实。对于尚未从招标文件抽取/人工确认的项目，正确状态应是 `method=unknown`、`award_mode=unknown`、`weights=null`、`committee_required=true`。

建议建立 `EvaluationPolicyService`：优先读取已确认招标政策；缺失时返回 unknown，并让 AI 只解释缺失，不替系统补全。

### P0-3 邀标候选召回仍可被无效历史报价污染

位置：`apps/api/services/supplier_recommend.py:234-253`

供应商评分聚合使用了 `valid_quote_filters()`，但最前面的候选召回查询没有使用该过滤器，也没有限制 active supplier。结果是：

- 测试/E2E/排除报价可以把某个供应商召回候选集；
- merged/inactive supplier 可能进入候选；
- 后续即使评分较低，候选身份本身已被污染。

位置：`apps/api/services/statistics.py:189-194`

`recommended_brands` 直接读取 Quote.brand，没有 join Supplier，也没有 `valid_quote_filters()`。这会把测试报价、无效供应商和报价自述品牌写回材料推荐品牌。

建议：

- 候选召回、统计评分、品牌证据统一走历史数据业务服务；
- 供应商必须 active；
- 品牌分成授权/代理证据、历史采购证据、报价自述三个等级；
- 报价文本中的品牌只能作为弱证据，不能直接认定代理关系。

### P0-4 超过 200 页会静默截断并被报告为完整

位置：

- `apps/api/intelligence/document_loader.py:24,77-82`
- `apps/api/intelligence/table_recognizer.py:389-391`

`MAX_PAGES_UNLIMITED` 实际是 200。`to_thumbnails()` 对真实页数取 `min(len(pdf), cap)`，recognizer 再把渲染出的数量当作 `total_pages`，没有传入 `truncated=True`。

因此 201+ 页 PDF 会被静默当成完整文档。这违反完整性门禁。

建议 DocumentLoader 返回 `{actual_pages, rendered_pages, truncated}`，质量报告使用真实页数并在截断时 BLOCKED。

### P0-5 生产 prompt 含真实供应商与品牌样本

位置：`apps/api/intelligence/prompts.py:168-179`

`TENDER_BRANDTABLE_PROMPT` 示例包含 KITZ、WATTS、BERMAD、凯硕、绵存、泰科龙等真实项目数据。这会给模型带来样本偏置，也违反仓库“不按现有文件硬编码”的要求。

建议替换为完全虚构的占位品牌和供应商，并用真实样本只做测试 fixture。

## 4. P1 发现

### P1-1 路由与服务职责过载

当前规模：

| 文件 | 行数 | 主要问题 |
|---|---:|---|
| `routes/analysis.py` | 2599 | session、匹配、复核、持久化、finalize、状态恢复混在同一路由模块 |
| `routes/quotes.py` | 903 | `batch_confirm` 同时校验、口径推导、供应商处理和持久化 |
| `routes/export.py` | 606 | scope/session 解析和导出格式编排耦合 |
| `services/bid_matrix.py` | 1513 | legacy matrix、anchor matrix、review matrix、基准、推荐、评标统计并存 |
| `intelligence/table_recognizer.py` | 1668 | 可接受但需要稳定内部边界，避免继续扩张 |

Claude 对“大函数、边界混乱”的判断成立。但“页面与导出完全各算一套矩阵”表述过度：anchor 主路径已经共同调用 `build_anchor_matrix()`；真正重复的是 session/scope 解析、finalization 和格式映射。

建议按业务边界拆分：

- `TenderSessionService`
- `SubmissionScopeService`
- `QuoteConfirmationService`
- `AlignmentService`
- `BidMatrixService`
- `EvaluationPolicyService`
- `BidExportService`

先抽权威服务和契约测试，再瘦路由；不要一次搬动全部文件。

### P1-2 submission 身份迁移未完全收口

新主路径正确使用 `BidSubmission.id`，`resolve_active_submissions()` 在显式 `submission_ids` 时也不会 union supplier 范围。

但仍有以下债务：

- `/anchor-review` 保留 supplier-id 旧路径；
- schema 和矩阵变量大量仍叫 `supplier_ids`，实际有时承载 submission ID；
- 注释称 supplier_ids “deprecated/ignored”，代码却仍明确启用 legacy supplier scope；
- legacy 路径无法自然表达未知供应商或同一供应商多次投标。

建议：新 API 契约只暴露 `submission_ids`；旧入口加 deprecation 标记和监控，确认无调用后删除。响应中同时提供 `submission_id` 与 `supplier_id`，禁止一个字段双重语义。

### P1-3 识别审计字段持久化为弱类型 JSON

Claude 认为来源和校验信息“完全没有持久化”并不准确。`routes/quotes.py:673-703` 已把 source_ref、税价原值、validation_flags、raw_qty、suggested_qty 写入 `extraction_meta`。

真实缺口是：

- `row_type`、`corrections` 未完整持久化；
- source_ref、flags、人工修正均为弱类型 JSON；
- 缺少字段级修改前后值和操作者；
- BQL 没有行级 `updated_at` 审计语义。

建议把高频质量字段结构化，保留 JSON 作为原始审计包；人工修正另建 append-only change log。

### P1-4 OperationLog 不足以满足字段级审计

位置：`apps/api/models/operation_log.py:9-19`

当前只有 user/module/action/target/result/remark/time，没有 structured before/after、project/session/submission/row identity。

建议新增领域审计事件：确认、修正、排除、重匹配、finalize、历史导入分别记录结构化 payload。

### P1-5 current session 查询口径不统一

部分调用同时要求 `is_current` 和 `status=confirmed`，部分仅取 `is_current`。这会使未确认 current session 被某些入口消费。

建议封装 `get_current_confirmed_session(project_id, category)`，禁止路由自行拼查询。

### P1-6 业务阈值散落

匹配阈值、checksum、序号/相似度、页面并发和页数上限分散在 route、service、env 与模块常量中。

建议区分：

- 系统资源配置：Settings/env；
- 领域安全阈值：集中 policy/config dataclass；
- 项目评标规则：EvaluationPolicy 数据。

## 5. P2 技术债

### P2-1 缺少版本化数据库迁移

`apps/api/core/database.py` 依赖 `Base.metadata.create_all()` 和大型 `_ensure_sqlite_schema()`，包含 ALTER、临时表重建和 PRAGMA 操作。

现有重建代码有外键/守恒检查，比无保护脚本好，但不适合长期演进和非 SQLite 环境。建议引入 Alembic，后续 schema 变更只走版本化 migration。

### P2-2 领域归一化逻辑重复

阀门 family/DN 逻辑同时存在于 canonical service、anchor_match 粗分类和其他 prompt/规则中。短期可运行，长期会产生识别、匹配、历史基准三个口径。

建议建立 `MaterialIdentityService`，输出 canonical family/DN/PN/unit，并保留 evidence/confidence。

### P2-3 匹配流程写 Material.extended_attrs

anchor match 会缓存 canonical 数据到材料主数据。它不直接污染价格，但让“只读比价”产生主数据写副作用。

建议把派生 canonical 存到独立缓存或显式 enrichment 服务，不在匹配函数中隐式写库。

## 10. 命名与状态规约

> 本节回答「目录、业务实体、业务服务命名是否准确，状态能否统一」。所有问题点均经 file:line 核查。这是结构治理（第三批），不阻断交付，但应在服务拆分前先敲定规约，避免拆分时把不一致的命名固化。

### 10.1 目录命名

- `intelligence/` 是清晰的限界上下文命名，保留。
- **`services/` 不是一层，是平铺杂物袋**：30 个文件混了四个上下文，无子包。建议按上下文分子包，并承载本文件建议的权威服务：

| 限界上下文 | 当前散落的文件 | 目标子包 / 服务 |
|---|---|---|
| 识别 / 物料身份归一 | `canonical` `standardize` `enhance` `category_classify` `brand_match` `source_reconcile` | `services/recognition/`；收口为 `MaterialIdentityService`（P2-2） |
| 招标比价主流程 | `anchor_match` `bid_matrix` `bid_alignment` `tender_list` `evaluation_policy` `bid_insight` | `services/comparison/`；拆出 `BidMatrixService` / `AlignmentService` / `EvaluationPolicyService` |
| 历史价格 / 主数据 | `comparison` `statistics` `scoring` `supplier_recommend` `supplier_resolve` | `services/history/`；收口为 `HistoricalPriceService`（P0-3 / rule） |
| 入库 | `import_service` `tabular_ingestion` `document_ingestion` `tender_pdf` | `services/ingestion/` |

- **`routes/analysis.py` 名称不准**：实际承载整条比价工作流（session / match / review / finalize / matrix / insight），应随 P1-1 拆分为 `tender_list` / `anchor_review` / `bid_matrix` / `alignment` 等域路由。

### 10.2 业务实体命名

**最严重一条：`TenderAnchor` 是规则文件反复声明的「矩阵行唯一主轴」，却没有 ORM 实体。** 无 `models/tender_anchor.py`；anchor 仅以 `TenderListSession` 内的 JSON + 到处传递的 `anchor_seq = String(20)`（`bid_alignment.py:38`）存在。最核心的权威概念是个字符串，是 anchor 链路到处用 seq 拼查询、口径难统一的结构性根因。建议将 TenderAnchor 升为一等实体（或至少一等值对象 + 稳定 ID）。

其余实体命名问题：

| 实体 | 问题 | 建议 |
|---|---|---|
| `Quote` vs `BidQuoteLine` | 两者都是「报价行」，名字不区分「历史价格事实」与「当前投标行」——这是 `supplier_id`/`submission_id` 双轨的词源 | `Quote` → `HistoricalPrice` / `PriceRecord` |
| `BidAlignmentGroup` / `BidAlignmentItem` | Group/Item 过泛；Group 实为「一条 canonical 比价行」，Item 为「归入该行的一份报价」 | `ComparisonLine` / `LineMember` |

### 10.4 状态统一（最高 ROI 的命名整改）

同一三态概念（好 / 待定 / 坏）在代码中被写成 **7 套词汇，且大小写不统一**：

| 语义 | 现存写法（各自字段） |
|---|---|
| 「好 / 通过」 | `ok`(row/eval) · `pass`(checksum) · `normal`(alert) · `safe`(match tier) · `firm`(rec) · `AUTO`(质量) · `confirmed`(生命周期) |
| 「待复核」 | `pending`(cell/row/item/lifecycle) · `REVIEW` · `partial`(row) · `conditional`(rec) · `risky_*`(match) · `basis_unconfirmed` / `alignment_pending` / `quantity_source_conflict`(eval) |
| 「坏 / 阻断」 | `BLOCKED`(大写,质量) · `blocked`(小写,rec) · `fail`(checksum) · `red`(alert) · `missing` / `invalid` / `excluded` |

**`BLOCKED` 与 `blocked` 同词不同大小写、不同字段——最易出 bug。**

更深层问题：`status` 一词被三条**正交轴**共用，导致 `pending` 一个值在六处含义不同（submission 生命周期 / group 生命周期 / cell 存在性 / row / item action / job）：

- **生命周期轴**：draft → confirmed → superseded → finalized → approved / rejected（session / group / submission / version）
- **存在性轴**：quoted / aggregated / pending / excluded / missing（cell）
- **可评标性轴**：ok / quantity_source_conflict / basis_unconfirmed / alignment_pending（eval）

且 `BidAlignmentItem` 持久层用 `action`(align/pending/exclude)，UI 层 `_build_review_cell` 派生成 `cell_status`(quoted/aggregated/pending/excluded/missing)，草稿层 `supplier_fill_llm` 又写 `status=`——同一概念三个名字三套值，边界硬映射。

**统一方案：**

1. **三条正交轴各起不重叠的名字**，一个词只属一条轴：`lifecycle_state` / `presence` / `evaluability`。禁止再用裸 `status` 兜底。
2. **每条轴定义集中 `Enum`**（新增 `core/enums.py`），取代满仓库字符串字面量。现仅 `bid_matrix` 有 `CELL_*` 常量是孤例。
3. **三态主词收敛到工程总纲 §3 已有的 `AUTO / REVIEW / BLOCKED`**，`ok/pass/normal/safe/firm` 等统一；大小写全仓库二选一固定。
4. **`action` 与 `cell_status` 合一**：持久层直接存权威 presence 枚举，展示层派生（`aggregated` 是 `quoted` 子态，靠 `agg_total` 区分，不必单列值）。

建议产出值映射表（旧值 → 新枚举），区分**纯改名（安全）**与**涉及 ORM 列 / API 契约（需迁移 + 前端同步）**两类，随第二/三批整改落地。
