# 比价流程的智能化分层

> 回答一个架构问题:在「招标清单 → 供应商报价 → 比价」全流程里,LLM 到底该做什么、做多少、在哪里复核。
> 目标是**一套机制覆盖所有品类**,而不是每种材料一套策略。
> 上游:`04-统一识别分析流程.md`(识别+分析的总流水线)。本文聚焦其中"智能"如何分层。

## 0. 核心命题

**LLM 全程只做一件事:消除"表达差异"——把同一个东西的不同写法,折叠成统一的规范表示。**

```
招标清单 ─┐                            ┌─ 比价
          ├─► [规范表示] ◄─── 匹配 ───►├
供应商报价 ─┘                            └─ 纯数学,无智能
```

比价本身不需要智能——到那一步,所有东西已经是规范的了。**智能全花在前面的"归一"上。** 这条命题决定了:不为任何单一品类写专用策略,只为"归一"这个通用动作建一套机制。

## 1. 四个品类无关的原子操作

整个流程的"智能"拆成 4 个原子操作,它们在不同位置反复出现:

| 原子操作 | 本质(消除什么差异) | 主要承担者 |
|---|---|---|
| **抽取** | 版面/扫描 → 字段(消除排版差异) | LLM(扫描件) / 代码(Excel) |
| **归一** | "真空磁环器"→"真空破坏器"、"300*150"→"300×150"(消除写法差异) | 嵌入 + LLM,**零硬编码词表** |
| **匹配** | 这条报价 = 哪个锚点行(消除命名差异) | 精确(代码)→ 召回(嵌入)→ 判定(LLM) |
| **裁决** | 聚合行、1:N 拆分、属性冲突如何处理 | LLM + 人工 |

**为什么归一不能用硬编码词表**:词表必然退化成"每种材料一套策略",无法覆盖 342 类材料。同义/OCR 纠错交给 AI 语义层(嵌入 + LLM),对任何品类都通用,是唯一可规模化的办法。

## 2. 智能化程度:中间高,两头低

智能不是均匀分布的。沿流程看是一条"倒 U":

| 流程步 | 智能化程度 | LLM 具体干的活 | 确定性 |
|---|---|---|---|
| ① 招标清单解析 | **极低** | 几乎不用;仅表头怪异时认列名 | 确定 |
| ② 供应商报价抽取 | **高** | OCR 后从 HTML 抽字段 + 逐行把规格/材质/型号归一成规范属性 | 不确定 → 需校验和 |
| ③ 锚点匹配 | **分层** | 精确匹配走代码(免费);只有残差(同义/OCR错/材质消歧/聚合)才上 LLM | 不确定 → 需复核 |
| ④ 比价计算/预警 | **零** | 完全不碰;纯数学 | 完全确定 |

**设计准则:刻意把工作往便宜、确定的两头挤,只把真正消除不了的表达差异留给 LLM。** 任何"能用代码/嵌入解决的"都不许调 LLM。

## 3. 机制 vs 数据:一套引擎,按品类只换数据

"不能每种材料一套策略"的落地方式 = 机制(代码)与策略(数据)分离:

| 层 | 一套通用代码 | 按品类变的纯数据/配置 |
|---|---|---|
| 清单解析 | 表头探测 + 列名同义映射(序号/名称/规格/数量),其余列进 freeform 属性 | 不写死列位置,靠列名识别 |
| 规范键 | 引擎读"哪些属性是身份键" | 由 `EXTENDED_ATTR_SCHEMAS` 中 role=匹配 的属性声明(阀门=阀型/DN/PN/材质;桥架=规格/表面/厚度) |
| 归一化 | AI 语义层(嵌入 + LLM) | **零词表** |
| 匹配引擎 | 一套分层算法 | 只换输入 schema,算法不变 |
| 锚点来源 | 一个抽象接口 | 招标清单(解析)/ 无清单(聚类合成) |

新品类进来,问的永远是同一组问题(规范 schema 是什么、哪些属性是身份键),而不是"再设计一套策略"。

**已验证**:降级路径 E2E 产出的 35 个阀门对齐组,没有一行阀门专用代码——是通用 LLM 对齐器吃 `category=阀门` 参数自己涌现的。通用机制已存在,锚点功能只是给它加"清单"这个锚点来源。

## 4. 锚点来源抽象:清单模式与降级模式共用一个引擎

匹配引擎的输入是"一组锚点行 + 一批待匹配报价行"。锚点行从哪来,是可替换的:

| 模式 | 锚点来源 | 对齐率(实测/预期) | 用户提示 |
|---|---|---|---|
| **锚点模式** | 招标清单解析出的标准条目 | 预期 80%+(待验证) | 正常 |
| **降级模式** | 无清单 → 对报价规范键聚类合成锚点 | 实测 30%(裸)/ ~50%(加归一上界) | "建议导入招标清单后重对齐" |

两种模式之后的匹配、复核、比价**完全相同**。只建一个匹配引擎,不为锚点模式单独造轮子。

## 5. 复核架构:三道闸门,两类复核

归一是 LLM 干的、不确定,所以**每一次归一都是一个待验证的"声明"**,必须经过闸门才能被信任、被写入比价矩阵、被缓存。

### 5.1 复核集中在"匹配边界"

归一发生在两处(抽取时的属性归一、匹配时的行→锚点归一),但**只在匹配边界设一道复核即可覆盖两者**:属性归一错了(如材质 不锈钢↔UPVC),会导致挂错锚点行,在匹配复核处暴露。不必逐属性复核。

### 5.2 三道闸门

```
报价行 ──归一/匹配(提议)──► 候选:挂到锚点#55, conf=0.7
                                  │
        ┌─────────────────────────▼─────────────────────────┐
        │ 闸① 自动校验 (代码,免费,确定)                       │
        │   归一出的 DN/材质是否真在原文?锚点数量 vs 报价数量? │
        └─────────────────────────┬─────────────────────────┘
                       通过 │              失败 → 直接进人工
        ┌─────────────────────────▼─────────────────────────┐
        │ 闸② LLM 复核 (独立一遍,对抗式)                      │
        │   换 prompt:"DN20 UPVC闸阀 真等于 锚点#55? 找反例"  │
        │   只对 低置信 或 缓存未命中 的跑;精确命中跳过        │
        └──────────┬──────────────────────────┬─────────────┘
            确认高置信│                    驳回/仍存疑│
                     ▼                            ▼
            写入比价矩阵 + 缓存            ┌──────────────────┐
            规范映射(下次免 LLM)          │ 闸③ 人工复核(终审)│
                                         │  只看残差:被驳回/  │
                                         │  材质冲突/聚合行   │
                                         │  裁决=最终事实+缓存│
                                         └──────────────────┘
```

### 5.3 两类复核的定位

| | LLM 复核(闸②) | 人工复核(闸③) |
|---|---|---|
| 位置 | 匹配提议后、写矩阵前,自动一道 | LLM 复核驳回/存疑后,残差队列 |
| 触发 | 低置信 或 缓存未命中(精确命中跳过) | 只有 LLM 都不敢确认的 |
| 性质 | 独立第二遍,对抗式找反例(**不是**同一次调用) | 系统终审,裁决 = 最终事实 |
| 产出 | 置信度;高则放行,低则降给人工 | 确认结果沉淀成缓存规范映射 |
| 规模 | 残差量,随缓存变厚而下降 | 极少数,目标趋近于零 |

## 6. 规范映射缓存:复核只做一次,LLM 份额随时间缩小

无论 LLM 还是人工,一旦确认一条映射("真空磁环器→真空破坏器"、"这条 UPVC 闸阀→锚点#55"),就写进**规范映射缓存**。下次同样表达直接命中,不再调 LLM、不再问人。

- 冷启动:LLM 份额高(无积累)
- 跑久了:缓存变厚 → 精确/规则层命中率上升 → LLM 只处理真正的新表达

这对 342 类材料的成本至关重要:**否则每标都全量调 LLM,贵且慢。系统越用越不依赖 LLM。**

## 7. 现状 vs 要新建

| 组件 | 现状 | 动作 |
|---|---|---|
| 通用 LLM 对齐器(category 参数) | ✅ 已有,降级模式可用 | 复用 |
| 比价矩阵 / 预警(纯数学) | ✅ 已有 | 复用 |
| 人工 confirm/reject UI + confidence | ✅ 已有(闸③雏形) | 复用,接入残差队列 |
| 招标清单解析(通用表格 → 锚点行) | ❌ 无 | **新建** |
| 锚点模式匹配(报价 → 固定锚点) | ❌ 无(现为涌现聚类) | **新建** |
| 闸② 独立 LLM 复核 | ❌ 无 | **新建** |
| 规范映射缓存 | ❌ 无 | **新建** |
| 规范键 schema(标 role=匹配) | ⚠️ 部分(`EXTENDED_ATTR_SCHEMAS` 有属性,未标身份键) | **补充标注** |

## 8. 待确认 / 开放问题

1. **缓存的键粒度**:规范映射缓存按"原始表达字符串"还是"原始表达的嵌入向量近邻"命中?字符串精确快但只挡完全相同;嵌入近邻能挡相似变体但有误命中风险。建议先字符串精确,观察命中率再决定是否上嵌入。
2. **闸② LLM 复核的触发阈值**:conf 多少以下才跑复核?需用本标数据标定(置信度分布 vs 实际错误率)。
3. **清单解析的兜底**:~~客户清单若无标准表头,退到 LLM 读表头~~ —— **已定(2026-06-08):第一版不管表头不规范,只吃规范表头跑通主干**。怪异表头退 LLM 留作后续迭代。
4. **规范键 schema 的归属**:身份键标注加在现有 `EXTENDED_ATTR_SCHEMAS`,还是独立一份"品类身份键"配置?(倾向前者,避免两份配置漂移)

## 9. 实现顺序

按"先量化、再生产"的稳妥顺序:

1. ✅ **清单解析器**(`apps/api/services/tender_list.py`)—— 实测:阀门清单 90/90 行、总量 1745 精确、材质消歧正确(闸阀DN20 拆 不锈钢#45/UPVC#55)
2. ✅ **锚点匹配测量**(`scripts/measure_anchor_alignment.py`,嵌入召回+DN核对,无LLM无词表)—— 见 §9.1 实测
3. **生产端点(进行中)**:上传清单→建锚点→嵌入匹配→落 `BidAlignmentGroup`→比价矩阵。**闸②LLM复核 + 缓存暂缓**,等真实使用看复核量再加(避免过度设计)。决策 2026-06-08。
4. (暂缓)闸②LLM复核 + 规范映射缓存 + 前端残差队列

### 9.1 锚点匹配实测基线(2026-06-08)

数据:project 60 三家阀门报价(82/87/44=213条)对 90 锚点行。

| 指标 | 降级裸对齐 | 锚点模式(嵌入+DN核对) |
|---|---|---|
| 报价匹配率 | 30% | 100%(召回,含需复核) |
| 可比锚点≥2家 | — | **65/90 = 72%** |
| 三家齐全行 | 3 | **19** |
| 置信度分布 | — | ≥0.85:128 / 0.70-0.85:83 / <0.70:仅2 |

验证结论:① 嵌入零词表可做通用归一(同义 0.99、材质消歧 UPVC↔不锈钢均正确);② **闸②复核确有必要**——清单无对应锚点时(球墨铸铁EPDM DN25)嵌入会强行挂最近的,误匹配只能靠复核拦;③ 复核量很小(可疑仅2条)。
保留:72% 为"≥2家可比+高置信",精度尚未用审批表真值做地面验证。

### 9.2 supplier_name 抽取的固有难点(2026-06-08)

投标文件含 4 类公司名:招标人(甲方)、投标人(卖方)、厂家/品牌商(如开滋KITZ)、代理商。
仅靠纯文本难可靠区分——投标人真名常在深处的盖章页,且 OCR 会丢失"投标单位名称"标签
(实测第9页标签被截成"称")。处理策略遵循「blank > wrong」:
- 投标人标签在封面且清晰(绵存/泰科龙)→ 正确提取
- 标签 OCR 丢失(凯硕)→ 返回空,交 filename 兜底或人工补填,**绝不确信地填成招标人/厂家**

prompt 已显式排除 招标人/厂家/代理商;深扫前 10 页早停。彻底解决需 VL 读盖章区(图像级,
类 fabric-bridge stamp 兜底),ROI 低,暂不做——supplier_name 是单字段,人工 2 秒可改。
