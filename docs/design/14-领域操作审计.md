核心结论：领域操作目前**完全没有审计轨迹**；且存在一个**只读 `OperationLog` 的现成查看器**。

## 2. 方案对比

### 方案 A：新建 `DomainAuditEvent` 独立表（审计原计划）
- 新表（event_type/project/session/submission/row/actor/before_json/after_json/created_at）+ `record_audit_event()` 服务 + 6 处埋点 + **新 GET 读接口 + 前端新查看页**。
- 忠于审计原文，结构最干净。
- **代价**：完整子系统。若只建表不配读接口/前端 → 只写死表（违背交付 ROI）。工作量大、跨后端+前端。

### 方案 B（推荐）：扩展 `OperationLog` + 复用现有查看器
- `OperationLog` 加结构化列：`before_json` / `after_json` / `project_id` / `session_id` / `submission_id` / `row_id`（均 nullable，走 Alembic 幂等迁移）。
- `write_log()` 向后兼容扩参，新增领域事件常量（confirm/correct/exclude/rematch/finalize/history_import）。
- 领域写入点调用扩展后的 `write_log`。
- 现有 `/logs` 查看器与导出**直接复用**（必要时补展示结构化字段）。
- **收益**：一张审计表 + 一个查看器；小、低风险、立即可见。
- **代价**：`OperationLog` 承载两类（系统操作 + 领域审计），靠 `module`/event_type 区分；JSON 列与扁平列混存（可接受）。

> 推荐方案 B。它直接回应审计对「扁平字段不足」的批评（补 before/after + 身份），又不另起子系统。

## 3. 方案 B 落地清单（实现时）

1. migration `0003_operation_log_audit_fields`（幂等）：加 6 个 nullable 列 + 必要索引（project_id/submission_id）。
2. `models/operation_log.py`：加对应列。
3. `routes/logs.py::write_log`：扩参 `before=None, after=None, project_id=None, session_id=None, submission_id=None, row_id=None`，序列化 JSON；旧调用零改动。
4. `core/` 或 `services/audit.py`：领域事件类型常量 + `record_domain_event()` 薄封装（统一 module 命名、actor 解析）。
5. 埋点（按价值/风险排序，可分批）：
   - 高价值低风险先行：batch-confirm（`routes/quotes.py`）、anchor finalize（`routes/analysis.py:2349`）、exclude/item-confirm。
   - 次批：rematch（match 路由）、历史导入（import_service）。
6. `/logs` 响应/前端：暴露结构化字段（按需）。
7. 测试：write_log 向后兼容；领域事件写入含身份 + before/after；`/logs` 过滤。

## 4. 与其他整改的关系
- 依赖 P2-1 Alembic（已就绪）：本设计的 schema 变更走 versioned migration。
- 与 P1-3 同源（行级审计语义）：`updated_at` 给「何时变」，本设计给「谁改了什么、前后值」。
