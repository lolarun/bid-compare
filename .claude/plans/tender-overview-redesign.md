## 1. 现在的问题

页面是「一个品类一张大卡片」的纵向堆叠，每张卡片里塞了四段内容（清单摘要 /
供应商表 / 历史轮次 / 推荐结论）。后果：

- 多品类时页面极长，看第二个品类要滚很久，品类之间无法对比；
- 项目级信息（编号、地点、状态、待校对份数）只有标题下一行小字 + 一条 alert
  横幅，项目本身"是什么、到哪了"没有稳定的落脚区；
- "现在该干什么"（`next_action`）只是卡片头上一个色块 tag，没有流程位置感——
  用户看不出这是五步里的第几步。

## 4. 必须遵守的约束（CLAUDE.md §4）

1. **Steps 当前步只能由后端 `next_action.code` 映射**，前端不得按"有没有清单 /
   有几份报价"另算一套判断——`next_action` 由后端 `derive_next_action` 唯一裁定。
   实现方式是一张纯展示映射表：

   | `next_action.code` | Steps 停在 |
   |---|---|
   | `pending_upload` | ① 上传识别 |
   | `list_unconfirmed` | ② 确认采购清单 |
   | `pending_intake` | ④ 校对确认 |
   | `ready_to_compare` | ⑤ 定标基准（未完成） |
   | `basis_set` | ⑤ 定标基准（已完成） |

   注：③ 报价入库没有独立的 code，由 `pending_intake` / `ready_to_compare` 覆盖；
   Steps 用 5 步是为了流程可读，映射表只有 5 个 code → 不新增业务语义。
2. **两个金额分列**：`detail_total`（系统算的）和 `declared_total`（文件封面写的）
   永远分开显示，`declared_total` 为 null 时显示"文件未声明"而不是 0。
3. **列身份是 `submission_id` 不是 `supplier_id`**：同一供应商可以有多份报价。
4. **待校对份数是项目粒度**，不能摊到品类 tab 里——后端明确说 job 上没有可靠品类。
5. **推荐结论仍只在 `axis_kind === 'tender_anchor'` 时出正式结论**，`quote_derived`
   只进预览通道（现有 `CategoryRecommendation.vue` 已经这么做，不改这条逻辑）。

## 5. 改动范围

- 重写 `ProjectOverviewView.vue` 的 template + style（script 的取数逻辑不动：
  仍是单次 `GET /api/projects/{id}/overview`，不新增接口）。
- `CategoryRecommendation.vue` 原样复用，挂到"推荐结论"tab 下。
- 顺带修一个现存缺口：`data === null`（加载中/加载失败）时模板没有任何分支，
  当前是白屏——补 `a-skeleton` + 失败重试。

**不做**：不动后端、不新增接口字段、不改 `next_action` 语义、不动比价工作台。
