# 上传报价时说清"归入哪一轮" — 方案待确认

状态：**方案待用户确认，未实施**（2026-09-03）
起因：用户反馈——从项目概览点「进入比价工作台」后，落在一个空的拖拽框上，
页面完全没说这次上传是**补充当前轮**还是**开新一轮**。

---

## 1. 缺陷的真实机制（不是按钮文案问题）

链路是断在**品类上下文**上，不是按钮名字：

1. 概览的 `goCompare()` 只 push `/workspace/:id/compare`，**不带品类**——
   哪怕用户当时正在看「阀门」。
2. `WorkspaceView.vue:44` 的 `category` 是个初始为 `''` 的本地 ref，
   **从不读 `route.query.category`**。
3. 轮次栏是 `v-if="category"`（`WorkspaceView.vue:1434`，注释写明"没有品类时
   不显示——轮次本来就是 (project, category) 维度的"）。

⇒ 品类为空 → 轮次栏整条不渲染 → 上传段没有任何轮次信息。截图里「阀门第 1 轮
收集中、已入库 3 家」明明存在，工作台却显示"0 份文件"、只字不提第 1 轮。

**轮次栏本身是好的**（轮次 chip、右键重命名/关闭/设为定标基准、`+ 开启新一轮`
带逐字后果说明的弹窗都已存在）。缺的是把用户带到那里时不丢上下文。

## 2. 顺带查出的一个真问题：存在"静默开轮"路径

`get_or_open_round` 的文档说的是"auto-creating **round 1** if none exists yet"，
但代码是：没有 **open** 轮 → 调 `create_round`，而 `create_round` 取
`seq = last.seq + 1`。

所以第 1、2 轮都已关闭时，用户确认一份报价 → **静默新建第 3 轮**，
全程没有看到那句"开启后当前轮次将关闭…"的后果说明。这跟本次缺陷是同一个
病根：轮次归属在用户看不见的地方被决定。

## 3. 为什么不建议照字面把主按钮改成「创建新一轮报价」

`create_round` 的第一句就是 **"closing whatever round was open before it"**。
把它做成概览页的主按钮，等于让"我只想再补一家供应商"的用户一键关掉当前轮。
（可挽回——`reopen_round` 存在——但要用户先知道轮次栏的右键菜单。）

另外首轮之前它也无意义：首轮按规格是**首次确认报价时**自动开的，
概览上提前给「开启新一轮」反而会造出空轮次（正是今天修的那条规格纠正的场景：
文件还在识别、或回 BLOCKED 永不确认，不该留下空轮）。

## 4. 方案：按钮说出目标轮次，开新轮永远是显式的次要动作

### 4.1 概览页：品类面板里给状态相关的动作（轮次是按品类的，动作也必须按品类）

| 品类状态 | 主按钮 | 次要动作 |
|---|---|---|
| 无轮次（还没确认过报价） | `上传报价 →` + 灰字"首轮将在首次确认报价时自动开启" | — |
| 有 open 轮 | **`上传报价到「第 N 轮」→`** | `开启新一轮…`（次要按钮） |
| 轮次全部关闭 | `开启新一轮…`（主） | `查看第 N 轮`（只读） |

第三行是故意的：全关状态下走上传会命中 §2 那条静默开轮路径。让它显式化。

### 4.2 传递品类，让轮次栏在工作台立刻可见

- `goCompare(category)` → `/workspace/:id/compare?category=<品类>`
- `WorkspaceView` 挂载时读 `route.query.category` 播种 `category` ref
  （`goAlign` 已经是这个写法，照抄即可）

### 4.3 工作台上传段加一条归属横幅

选中品类且有 open 轮时，拖拽框上方常驻一句：

> 本次上传将归入 **第 N 轮**（收集中）。 [改为开启新一轮…]

这是对用户原话最直接的回答——**在放文件的那一刻**告诉他归到哪一轮。

### 4.4 复用，不新建

`开启新一轮…` 一律唤起 **WorkspaceView 里已有的那个弹窗**（已含逐字后果说明）。
不在概览页复制第二套轮次管理 UI——否则两处迟早说两套话。

## 5. 改动范围

- `ProjectOverviewView.vue`：品类面板加状态相关动作按钮；`goCompare` 带品类
- `WorkspaceView.vue`：读 `route.query.category`；上传段归属横幅；
  把新建轮弹窗做成可被 query 参数（如 `?newRound=1`）直接唤起
- **不动后端**。§2 那条静默开轮是否要改（例如全关状态下拒绝隐式开轮、
  要求显式确认）单列，见下。

## 6. 用 docs/test2 真实材料复核（2026-09-03）

材料：临港中科院项目，母线槽 + 潜水泵**两个品类各两轮**，含每轮的
回标 PDF、开标汇总记录、采购会议纪要、招标结果审核表。

### 6.1 方案前提被证实（更强了）

轮次是**正式事件**，不是"又传了一批文件"：母线一轮 2024.11.08「开标」、
二轮 2024.12.04「询标」；潜水泵二轮纪要写明"根据首轮开标结果，组织…询标"。
每轮各有邀请名单、实收份数、汇总表和会议纪要。用户当然知道自己在传哪一轮
——把归属藏起来确实是缺陷。

### 6.2 方案里一处**假设错了**

我按"每家供应商一个文件"设计了「上传报价到第 N 轮」。真实材料是
**一轮一份合订回标 PDF**（`中科院母线第一轮回标.pdf` 11 页：第 1 页就是
开标汇总表，后 10 页是各家明细）。上传单位是轮次级的，文案与心智模型应改成
**「导入第 N 轮回标（一份含 N 家）」**。

### 6.3 材料暴露的三个更深问题（都不是版面能解决的）

**A. 同一列里混着不可比口径——最严重，且我刚做的设计踩进去了。**
母线第一轮：都安 827,034「**不含安装**」，其余三家「含安装」。按最低价排序，
都安第一——它便宜只因为没含安装。二轮都安改含安装，827,034 → 1,024,072
（+197k）不是涨价，是范围变了。
另有铜价基准：一轮四家各报各的（77540/76600/77470/77680 元/吨），
二轮统一到 73410。
系统 `price_basis` 只建模含税/不含税，**含/不含安装、铜价基准都不存在**。

→ 对本页设计的直接影响：轮次卡上的「明细合计区间」放到母线第一轮，就是拿
"不含安装"和"含安装"算区间。tooltip 写了"不是评标总价"仍然不够——**区间这个
形式本身就在邀请比较**。这是我的设计缺陷。

**B. 轮次性质对不上词汇表。** 他们的会议纪要表头是三选一勾选框
「开标☑ / 评标□ / 询标☑」。系统 `QuoteRoundStage` 只有 `pre_tender | formal`。

**C. 邀请是按轮次的，模型不是。** 母线"邀请四家…实收标书三份"。
`BidInvitation` 挂在 `tender_id` 上、**没有 `round_id`**，且它是邀标建议服务的
产物（pending/sent/responded/declined），不是开标记录里那份名单。
（据此更正我上一轮的评审结论：我说原型的"供应商参与 X 家 / 报价已确认 Y 家"
没有业务依据——**这个判断是错的**，业务确实需要"应邀 vs 实收"，只是系统存不了。）

**D. 价格与商务条件的交换看不见。** 潜水泵二轮三家全部涨价
（凯泉 371,766→394,498；东方 383,949→420,078；俊能 355,880→360,260）；
同时俊能把付款条件从"两月后付 70%"改成"一月付 95%（50%商票）+ 银行保函付至
100%"。涨 4,380 换回款大幅提前——纯价格排序会判成"变贵了"。
开标汇总表的商务列（税率 / 资金支付条件 / 质保或售后 / 其它承诺）系统一列都没存。

**E. 评选办法其实写在文件里。** 纪要明写"**合理最低价**方式评选"，定标理由是
"资质等级、技术、服务、资金、社会信誉…且投标价格为本次招标的最低价"。
而 `get_evaluation_policy` 对所有项目返回 UNKNOWN——不是招标文件没有，是
**系统没去读**。且"合理最低价" ≠ "最低价"。

### 6.4 据此修订本方案

1. **轮次卡去掉"区间"这种邀请比较的形式**：改为逐家列示；同轮存在不同口径时
   （安装范围/铜价基准/付款条件不一致）明确标注「口径不一致，不可直接比较」。
   在系统能识别这些口径之前，宁可不给聚合数。
2. 上传入口文案改为轮次级「导入第 N 轮回标」。
3. 新建轮弹窗需采集：**性质（开标/询标/评标）、日期、邀请名单**；
   现在只有名称+阶段+备注，采不到"邀请四家实收三份"。
4. `QuoteRoundStage` 词汇表扩到 开标/询标/评标（**后端变更**，单独排期）。
5. A/C/D/E 四个缺口都是后端与识别层的事，不要塞进这一轮版面改动。

### 6.5 一个附带观察

母线一轮纪要写"实收标书三份"，但开标汇总表里有**四行**报价。他们自己的记录就
不一致——系统必须能容纳这种不一致（记录原文 + 标疑点），不能靠"总有一个是对的"
去做静默取舍。
