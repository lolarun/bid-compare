## `docs/design/41` —— 认真调研 qwen-vl-ocr 能否替代 Paddle（2026-08-24，方案已写，未实现）

跟下面「Paddle 页面分类降本实验」是**两件不同的事**，别混：那条是"筛页后仍然用
Paddle 解析"的省钱路线；这条是"整个换引擎"的更大调查，问的是"Paddle 能不能被
别的模型替代"。

**起因是一次纠错。** design/26 当年把 Paddle 拿去对比的是 `qwen3.7-plus`——一个
通用对话模型，不是 `qwen-vl-ocr-latest`——DashScope 专门做 OCR 的模型
（`ocr_options={"task":"table_parsing"}`，代码里早就有、只在这个项目最早期的
1-2 份文档原型测试里用过一次，从没跟 Paddle 正面比过）。

**1 页 5 行的抽样（不是结论）**：单价 5/5 对、合价 4/5 对（唯一错的那行是
qty=1，单价合价理应相等，答案是一个跟表里任何数字都对不上的幻觉值）；表头
本身漏了一列（"专业"，数据行里"给排水"这个值有归属，表头没有列名接它）——
这会让任何按位置对齐表头的解析直接错位，是真实的工程隐患，跟"这行答对没
答对"是两回事。

**API 成本不是问题**：单页实测 5771 token，按公开单价（¥0.3/¥0.5 每百万
token）算，159 页全语料一次约 ¥0.5——比 Paddle 便宜约 30 倍。**真正的成本是
工程量**：要跟当年测 Paddle 同等严谨度（design/26 §6 那张表），得写一套
HTML 表格解析器 + 复用 `column_roles.py`（design/40）的列映射 + 复用
`test_scenarios_e2e.py` 的标准答案和打分口径，跑满 7 份文档、逐字段比对——
不是调一次 API 就完事。

design/41 §6 三个待决：①表头/数据行列数对不上时的处理策略；②一次测 7 份还是
先测 2 份;③解析器放哪（建议 `scripts/`，只读语料，不碰生产代码，跟今天的
`try_page_classify_gate.py` 同一个先例）。**这份文档只是测量计划，不是决定要
换引擎**——测完什么样，要不要真的换，是另一次决策。

## design/41 分类筛页已接入（2026-08-24，**默认关闭**，未上生产）

用户："新增分类筛页到识别链路 / 把 qwen 职责迁到 mimo / 优化速度"——三件都做了。

### 1. 分类筛页 → `apps/api/intelligence/page_filter.py` + `pipeline.py`

**默认关闭**：没配 `MIMO_API_KEY` 时 `select_pages` 返回"全送"，这条链路逐字节
等于接入前。开启需要显式配 key。

**三道防线，全部有测试钉住（先红后绿验证过）**：

1. **多轮取并集**（`FILTER_ROUNDS=2`）。实测同一份文档两轮结果不同——第一轮漏
   了第 11/12/13 页、第二轮零漏。**模型有真实 run-to-run 波动，单轮结果不可信**
   （我先前汇报"9 份全过、假阴性 0/62"时每份只跑一轮，那个结论本身不牢靠，
   已在此更正）。并集之后只有"每轮都判否"的页才跳过，波动从风险变成保护。
2. **一切存疑都送**。窗口调用失败、模型漏答某页、解析不出判定行、渲染不出图
   ——任何一种都计入送检。判据是"只有明确判否才跳过"，不是"没判真就跳过"。
   拆掉这条防线，3 条测试立刻红。
3. **台账必须闭合**。`total == sent + skipped`，逐页留跳过理由，写进
   `draft.meta["page_filter"]`。台账不闭合时**整份送**，不带着这个状态往下走。

### 2. qwen → mimo：**逐项切，不是一次性硬换**

qwen 在生产里担着**四项**职责，失败后果各不相同：

| 职责 | 后果 | 状态 |
|---|---|---|
| 封面标量（`bid_total`） | **最重**，喂声明总价核对门 | ✅ 实测 mimo 全对，连税基 `tax_included` 都判对 |
| 招标要求抽取 | 中 | 同一开关，未单独实测 |
| 卡片概述 | 轻（文案） | 同一开关，未单独实测 |
| 扫描件招/投标分类 | 中（路由错类型） | **视觉调用，不走这个开关，未迁移** |

开关是 `domain_config.TEXT_CLIENT_VENDOR`（`'dashscope'`|`'mimo'`），**默认
`dashscope` = 现状不变**。配了 `mimo` 却没有 key 时**明确回落并记日志**，不静默
降级（有测试断言日志必须留下）。

### 3. 速度：修了两处并发疏漏，但**端到端仍然变慢**

两处都是我自己写串行写出来的，没有任何理由：
- **窗口之间**本来就独立（重叠只在窗口内部提供上下文，不跨调用传状态）
- **轮次之间**也独立（取并集，不传递状态）

改成并发后，泰科龙 53 页分类从**几分钟 → 136.7s → 58.7s**。

**但必须如实说：这个功能让端到端变慢了。**

| | 现状（不筛页） | 筛页后 |
|---|---|---|
| 渲染 | 11.4s | 11.4s |
| 分类 | — | **58.7s** |
| Paddle | 49s（53 页） | 10s（11 页） |
| **合计** | **60s** | **80s（慢 33%）** |
| **Paddle 成本** | ¥4.77 | **¥0.99（省 79%）** |

**用 33% 的等待时间换 79% 的成本**。这是产品权衡，不是技术问题——需要你决定
划不划算。若要更快，可以把 `FILTER_ROUNDS` 降到 1（分类减半到 ~30s，端到端
约 51s，反而比现状快），但那样就**放弃了防线一**，而防线一正是实测到波动之后
加的。我不建议默认这么做。

### 还没做的

- **9 份全量只跑过单轮**，用两轮并集重跑一遍才算数
- `--reparse` 端到端未验证：命中页真送 Paddle 后，行数/合价合计对不对得上基线
- 视觉类职责（扫描件分类、gap_fill）未迁 mimo
- 一次性送 53 页**实测整批失败**（模型要一次输出 53 行判定，输出过长），
  这条路已排除，窗口化是必需的

全量后端测试 **1131 passed / 0 failed**（新增 14 条筛页 + 3 条切换开关）。

## Paddle 页面分类降本实验（2026-08-24，三轮实测完毕，结论：**账成立、但还不能上生产**）

客户反馈 PaddleOCR-VL ¥0.09/页贵。查证经过（全程可复算，不是拍脑袋）：

**先纠正一句我自己说错的话。** 讨论"分类后只送清单页"这个思路时，我起初说
"分类每页要先渲染+过一遍模型，那笔钱跟直接整份送 Paddle 是同一个量级"——这是
没查 qwen 实际单价说的一句猜测。用 qwen-vl-plus 的真实输入单价（¥0.0015/千
token）算，单页分类成本约 ¥0.003，量级上比 Paddle 的 ¥0.09/页便宜 **30 倍**，
不是"同一个量级"。这句话是错的，已撤回。

**账本身是站得住的。** 语料库 7 份投标 PDF（招标 PDF 有文字层，走 `text_layer`
直抽，**根本不进 Paddle 账单**，之前的成本对比漏了这条，一并订正）：

| | 页数 | Paddle 单价 |
|---|---:|---:|
| 全部投标 PDF（现状，整份送） | 159 | ¥14.31 |
| 只送"贡献行的页"（理论上限，2026-08-23 从真实识别产物量出） | 58 | ¥5.22 |
| qwen 先分类（159 页 × ¥0.003 ≈ ¥0.49）+ 只送命中页 | 159→58(若准) | ¥0.49+¥5.22=¥5.71 |

分类方案的账面收益（约 60%）非常接近理论上限（64%），差距就是分类本身那 ¥0.49。

**但这条路有一个现有机制都没有的风险，账算得再漂亮也绕不开。** design/33 的
补位处理的是"Paddle 看过这页、格子读不到"——**有信号**（`AMOUNT_EMPTY`），能在
信号上建验证门。这条路不一样：qwen 判"这页不是报价页"之后，**这一页从头到尾
没被 Paddle 看过**，报价行是静默消失、没有任何下游信号能发现的——不是空格子，
是压根不存在的行。`.claude/rules/recognition.md` 那条「识别必须覆盖文档实际
页数…禁止静默截断」正是为了防这个。

浪费页的分布也很不均匀，不是每份文档都值得分类：

| 文档 | 贡献行的页/总页 | 浪费占比 |
|---|---|---:|
| 泰科龙 | 10/53 | 81% |
| 绵存 | 6/31 | 81% |
| 凯硕 | 4/19 | 79% |
| 浦东 | 7/15 | 53% |
| 宏胜 | 7/11 | 36% |
| 远东 | 15/19 | 21% |
| 亨通 | 9/11 | 18% |

60% 的理论省钱几乎全部来自前三份（资质证书/技术规格书占了大半篇幅），亨通/
远东本来废页就不多，分类了也省不了几个钱，却一样要担误判风险。

**在动生产代码之前，先测分类器准不准**——`scripts/try_page_classify_gate.py`。
渲染缩略图（复用 `DocumentLoader.render_pages`，跟生产识别同一套 pdfium 调用）
→ qwen 逐页判"是不是报价清单页" + 一句话概述（复用 `DashScopeOCRProvider`，
跟生产报价识别/方向预检同一个 provider 类）→ 跟已知的"贡献行的页"逐页比对，
**假阴性**（该留的页被判掉，最危险的一类）单独算 → `--reparse` 时把命中页
重新拼一份 PDF 真送一次 Paddle，验证这条链路产出的行数/合价合计对不对得上
整份送的基线。

只读 `tests/fixtures/documents/` 真实 PDF，只写 `outputs/page_classify_gate/`
（已 gitignore），不碰生产代码、不落库。

### 第一版实测：逐页独立发送，recall 0.2，问题定位到位

先拿两份招标文件当诊断样本（招标 PDF 本身零成本、不进 Paddle 账单，测的不是
"值不值得给它们省钱"，是拿一正一负两个已知真值的样本先探分类器准不准）：

- **徐汇招标文件（负样本，全篇无报价表）**：11/11 判对，而且不是偷懒答"否"——
  第 3 页模型明确说"表格无单价合价仅列材料名称规格"，证明它真的看了表格结构。
- **金桥招标文件（正样本，第 14-18 页是嵌在 PDF 里的完整 89 项清单）**：
  **recall 只有 0.2**，第 14 页判对，**15-18 页全部漏判**（假阴性）。

**根因不是模型判断力不够，是脚本自己的设计缺陷**——第一版 `_classify_one` 每次
只送一张图（`vl_extract_csv([png], ...)`），页与页互相看不到。金桥这份清单的
表头只印在第 14 页，15-18 页是续页、不重复表头，模型单独看一页确实看不出那几
列数字是"单价""合价"，理由写的是"无单价合价列仅规格数量"——这是诚实的
"看不到证据"，不是瞎猜。这正是脚本设计之初就点名的风险（假阴性=报价行静默
消失、没有下游信号），第一次实测就撞上了，测试起到了它该起的作用。

### 修复：整份一次性送，页前插 `PAGE_<n>` 标签，复测 5/5

改法不是碰运气调提示词，是复用仓库里已有的约定——`dashscope_ocr.py` 的
`vl_extract_csv(images, prompt, labels=[...])`，方向预检早就在用"每张图前插
`PAGE_<n>_ROT_<deg>` 标签"这套模式（那处注释自己写着"不交错标签会串页"）。
提示词里显式教它认续页："某页看不到表头，但版式跟上一个报价表页明显延续——
同一类条目继续往下排、右边也是数字，只是没有列名——也判 is_quote_page=true"。

复测（`classify_doc`，`classify_doc_per_page` 保留做对照，不再是默认路径）：

- **金桥招标文件：recall 1.0，precision 1.0，0 假阴性。** 15-18 页全部判对，
  理由分别是"续接上一页报价表"，第 18 页的概述准确到"同一张表末尾83-89行及
  合计行"。第 12 页（合同模板附件列表）、第 13 页（单行示例表）仍正确判否——
  不是"改成什么都判真"这种反向过拟合，是真的做了跨页结构推理。
- **徐汇招标文件：11/11 仍然全部判对**，确认改法没有引入"逢表就判续页"的
  新偏差。

### 真实投标 PDF 实测（泰科龙 53 页）：三轮对比，结论是"还不能上生产"

招标文件那两份是零成本的诊断样本；真正要回答的是**真花钱的投标 PDF 上行不行**。
泰科龙是最难的一份（53 页、报价表横跨 5-14 页、封面带红章），三种模式全测过：

| 模式 | recall | 假阴性 | 失败性质 |
|---|---:|---:|---|
| qwen 整份一次送 | **0.0** | 53/53 | 2 页红章触发内容审查 → **整份请求全灭** |
| qwen 分窗口+重试 | **0.5** | 5/10 | 2 页硬拒（HTTP 400，重试也过不去）+ 3 页判错 |
| ernie 分窗口+重试 | **0.8** | 2/10 | 2 页软拒（HTTP 200 但回拒答话术），1 页重试后给了错答案 |
| **gemini-3.6-flash 分窗口** | **1.0** | **0/10** | **零拒答、零报错**；仅 1 页误报（多送 ¥0.09，不丢数据） |

**一处要更正我自己先前说错的话。** 我一度把"qwen 连报价页都认不出来"当结论讲，

### 顺带查出的系统性缺陷：`source_ref` 页码/行号在续页上是错的

`source_ref.page` 取自 `begin` 页，`row` 是合并后表内的行序，续页的行全部标错：

难点：Paddle 的 table `cells[].position` 全是 `None`，没有几何可以拆回物理页。

### 方向假说：已用真实 API 双臂实验证伪（2026-08-22）

只差 `/Rotate` 一个属性、图像流完全相同的两份两页 PDF，各跑 3 次：

| B 预转正 | `/Rotate=0`（内容正立，已渲染确认） | **只剩 seq 24-37**，第 2 页塌成 1 行 |

1. **预转正不但没修好，反而把召回打崩**——方向假说对 Paddle 这条链**证伪**。

## 手工测试三条反馈之二（2026-08-23 深夜，明细页）

**① 明细页卡顿 → 三个深度监听器改成标量监听。** `WorkspaceView` 里三个
`watch(batchFiles, …, { deep: true })` 需要的**只是每份文件的标量**(id/状态/是否
已入库/供应商名/份数),一个都用不到 `items` 里那 100+ 行明细。deep 监听让 Vue 要
遍历 4 份 × 136 行 × 十几个字段 ≈ 8000 个响应式属性来建依赖,而且**用户在表格里
改任何一个格子**都会把三个 watcher 全部叫醒、整体重新遍历一遍。回调里的
`refreshDryRun`/`fetchSupplierSummary` 各自有幂等守卫、不会真发请求,但遍历的代价
照付。改成观察一个标量签名字符串 `batchFileSignal`：编辑单元格不再触发,新增/删除
文件、识别完成、入库完成、改供应商名这些真正该触发的一个不落。

**② 「原文无合价」到底是不是缺陷 —— 标准答案里有,而且记的是"明确不报价"。**
`亨通 / HYA-2*0.5` 那行,标准答案的核对说明列原文写着「PDF原表单价、合价均标为/」
——原表那两格印的是 `/`,是投标方**明确不报此项**,不是系统读不到。但 CSV/xlsx
转换把 `/` 弄丢了:它只留在核对说明列的文字里,单价合价两格本身变成纯空白。后端
判"明确不报价"靠 `classify_amount_cell` 看**格子自身**的取值(认 `/`、`—`、`无`
等整格标记),在这个容器里确实没有证据,于是按 CLAUDE.md「不得把"明确不报价"与
"读不到"合并」的要求来问人。**行为是对的,但它手里有证据却没端出来**——备注字段
后端一直读得到,只是从没写进 `missing_total_rows`。现已随行返回。

**③ 点「确认入库」没反应 → 对话框只有一个不做事的按钮。** 那是 `Modal.info`,
唯一的「去核对这些行」按钮 `resolve(false)`,除了跳转什么也不做;提示语却写着
「或确认原文确实未报价后再重新点击校对入库」——**界面上根本没有做这件事的控件**。
后端其实一直认 `item.not_quoted`(`or bool(item.get("not_quoted"))`,不阻断),缺的
只是前端把这句话传回去的通道。现在:显示了全部待确认行时给出「确认未报价,继续
入库」,写回 `not_quoted` 后自动重试(复用 checksum 那条"请调用方重试"协议)。
**安全线**:只有 `rows.length >= totalCount`(这次弹窗真的显示了全部行)才给这个

新增测试:`test_not_quoted_confirm.py` 3 条(备注随行返回 / 标记让该行真正入库且
`total_price` 为 None / **标记不豁免整份文件**,同批没打标记的行继续被拦)、

## 手工测试三条反馈（2026-08-23 晚，均已修）

**① 金桥采购清单没被认成采购清单 → 已改判。** 它的价格列**一个真实价格都没有**:
`单价(元)不含税` 整列空,`合计(元)不含税`/`税额(元)`/`价税合计(元)` 三列非空取值

文件"→ **采购清单变成了比价矩阵里的一列供应商**(0/89、合计 ¥0)。类别错误,不是
置信度问题。两处补齐:整列全零的价格列不算价格列;补上「有价格表头但格子几乎全空
→ 空白清单表」这一支(原来只有"几乎全满→报价单"和"压根没价格列→清单",最典型的

改用**合成的半填样本**守——判据边界该由合成样本守,业务事实才需要真实语料。

**② 徐汇采购清单 170 —— 核实无误。** 从原始工作簿独立重数:矿物电缆 78 + 普通电缆
92 = 170 有序号数据行;另有 14 条续行(序号空,是复合行的分解子行,不该单独成锚点)和
2 条表尾「备注:铜价…」,都正确排除。界面上 `136/170 有单价` 也对得上——那 34 条

标签页里,预览这屏看不见)。用户口径:**直接进比价,在比价页给提示**。现在点一下先

## 列→角色：词表→验证→模型兜底（`docs/design/40`，L1 已实现）

2026-08-23。用户提的是泛化:采购清单和报价清单列名几乎没一次一样(光"名称"就有
`名称/品名/项目名称/材料/设备名称` 四种,徐汇采购清单**根本没有规格列**),靠往关键词表
加同义词走不远。

**顺序不可交换:词表先跑 → 确定性验证 → 验不过才问模型 → 再验一次。**
验证器(`intelligence/column_roles.verify_roles`)只问证据:数值列能否解析成数、名称列
是不是文本、**同税基**下 `数量×单价≈合价` 闭不闭合。它对提议来源中立,这正是它能当
闸门的原因。九份零模型语料**全部走词表、零模型调用、行数一字未变**(用会炸的桩钉住)。

`_doc_meta.column_source` 留痕三态:`keyword` / `llm` / `keyword_unverified`(后者带
未通过理由——验不过≠解析不出,漏认一个可选列不该拒掉整份上传)。

招标侧多一坎:表头写成词表不认识的字时**连表头在第几行都定位不到**,所以那边用的是
`propose_layout_by_llm`(表头行+列角色一起要)。

**一条如实记录的局限**:乘法可交换,验证器**抓不出"数量↔单价对调"** —— 我最初那条
测试断言"算术能抓",跑一遍就被推翻了,现在把真相钉住。单文件没有证据能证伪它(数量
不总是整数:1905.25、2882.94),真能证伪的是跨供应商证据,那要到对齐阶段才有。风险
在接线层收窄:词表只是**缺角色**时,模型只准填空、不准改写词表已认出的角色
(`_only_missing`)。

**边界已写进 `.claude/rules/recognition.md`**:列映射可以用模型(表结构解释,一表一次,
产出必过验证),**行对齐不可以**(数量序列已确定性解到 100%,且行级错配没有独立证据
可证伪——那正是 CLAUDE.md「LLM 不得重排候选」守的东西)。

**§7 记了没做的 L0**:Paddle 那条链路目前是 `cells/matrix 网格 → 拍平成 CSV 文本 →
再从文本猜回列身份`。`_classify_trailing_cells` 的注释自己写着尾部列是**逐行**按算术
认的、**不管表头写什么** —— 逐行猜就是逐行可能错,design/34 的行内错位和 design/37 的
跨行错位都是这个的下游症状。修法是去掉 CSV 往返、按 `matrix` 的列下标一次性定角色。
**没做的原因**:它会动到全部七份快照基线,需要自己的一轮 before/after 实测,我不在
无人复核时动它。

## 零模型用例 A3/B3 已 100% 对齐（`docs/design/39`，已实现）

2026-08-23。A3(金桥 采购清单+3 份报价 xlsx)、B3(徐汇 采购清单+4 份报价 csv)
走的是**完全确定性**链路——不识别、不嵌入、不调模型。这种情况下对不齐只能是
代码缺陷。三个独立缺陷挡在路上,都不是"匹配很难":

| | 行轴 | 每家报价 | 改前对齐 | **改后** |
|---|---|---|---|---|
| A3 | 89 | 89 | 整份被 422 拒(测试 skip) | **89 / 0 pending / 0 residue** |
| B3 | 92→**170** | 136 | 79 (58%) | **136 / 0 pending / 0 residue** |

1. **三列价格没有字段可落**。泰科龙那份只印「不含税单价 + 价税合计」,而
   `_TABULAR_COLUMN_PATTERNS` 只有一个税基槽,`合计(不含税)/税率/税额` 读出来
   直接扔,于是不含税单价被迫配含税合价,89 行全 `tax_basis_suspect`。算术层
   一直是对的(`_PRICE_PAIRS` 的注释早就写着"比错了尺子"),只是拿不到数据。
   修法是补齐六个税基槽,**有效价一分没变**(泰科龙 78.1/凯硕 71/绵存 93)。
   原先记的"需要加字段+迁移,超出范围"是误判——不需要迁移,需要六条列判据。
2. **半份采购清单从没被解析**。徐汇是两个 sheet,预览只读 `pick_default_sheet`
   挑的那一张。已改 `parse_tender_all_sheets` 合并(汇总表按 `_FOOTER_MARKERS`
   排除),sheet 名进 `profession`——这份清单的列只有 序号/名称/单位/数量,
   矿物/普通这个信息**只存在于 sheet 名里**。
3. **"只报一部分"被当成"没法对齐"**。顺序直连第一道门禁是 `行数==锚点数`。
   四家各报 136/170(正好 矿物 1..44 + 普通全部,余下 34 条 `RTXMY-*` 一家没报,
   逐行核对过)。新增**保序子序列直连**:左右双向贪心互证唯一性,只在数量可行的
   候选之间用文本断同分(文本**绝不创造匹配**),任何一行断不开则整份回落语义。
   实测 135/136 行左右自动一致,1 行需断同分,四家结果与人工真值逐行一致。

E2E 用 `_ZERO_MODEL_FULL_ALIGNMENT` 钉死,**零容差**:每家必须 matched==quote_rows
且 pending/residue/validation_failed 全 0。已验证故意改错基线会红。

**§7 留了个未决问题**:列映射仍是关键词表,下一份写「除税单价」的表还得再加。
这件事该交给大模型(schema 解释,且可用算术确定性验证),但**行对齐不该**——
数量序列已经确定性可解,那是 CLAUDE.md「LLM 不得重排候选」的正面战场。

## 3. 其他已验证的事实

### 自校验：不需要 golden 就能说出自己错了多少（**仅离线，未接生产**）

明细求和 vs **该产物自己抽到的合计行**（`cable_diff_report.document_total`）：
**8/11 的自校验差与真实差完全相等**，其余会主动报「无法闭环」。
⚠ 这是**评测脚本里的函数**，生产链不调用；且它默认容差 1%、只诊断不阻断。
清单常分章节各出一个合计，故候选包含「单一合计」与「章节合计之和」两种。

### 提示词

约束分两类：**告诉模型「怎么看」有害**（"按原始左右顺序输出列"让侧向页整张表转置）；
**告诉模型「输出什么」有用**（业务语义，模型无从推断）。

现行三条业务规则（`PROMPT_DOC`）：
1. 保留小计/合计/总计行并标 `row_type` —— 换来免 golden 的闭环自检；
2. 不许补算合价，读不到就留空；
3. 同一清单重复出现时照实全部输出，标 `copy_no`。

规则 ③ 在 3.7 系列上工作正常（浦东 128/128 两份副本）；旧模型 3-vl-plus 会把它当页
计数（1..9），那时不能用它筛行。

**注意**：这条原则**不能推广到方向判定**——§2 里"说明目的"的写法只在判横竖时更好。

### LLM 文本复核会改坏真值

实测：把抽好的 CSV 加上「明细合计 X、声明总价 Y、差 Z」交给模型修正，它**没有编造行**
（正确），但把**官方声明总价改成了抽错的那个数**，并给出"应以 X 为准"的结论。后果是
唯一的真值被抹掉、闭环从此永远通过、缺口永久隐藏。

**文本层复核解决不了税基取错、字段留空**——从文本看它们完全自洽，矛盾只存在于原始页面。
正确做法：闭环定位 → 圈可疑行 → **回像素重读** → 重新闭环。
**LLM 的职责是「再看一眼原图并转录」，不是「把账做平」。**

## 6. 方法论教训（本轮代价最大的部分）

1. **不要用单次结果做决策。** 本轮至少三次因此走错：选 flash 做方向（单次 10/11 → 七份
   55,952 元）、砍掉 180° 维（单次实验 → 七份 309,526 元）、选"两问+对比图"（单次 11/11）。
   稳定性对照做出来才发现**所有方案都在 3/10 到 11/11 之间跳**。
2. **换尺子不算进步，用错尺子也会低估。** 「宏胜 109/136」是规格文本对齐的结果，
   按行序保序对齐是 135/136。评分口径必须与业务口径一致。
3. **先做单变量对照，再下因果结论。** "180° 代价 −25.6 万"是把轴向差异算进去了，
   单变量对照下是 −129,532。
4. **验证判据必须能区分你要区分的东西。** 算术闭合验证不了 180°，因为模型读倒置页
   一样准——账一样平。选判据前先问"这个判据在错误情形下会不会也通过"。
5. **不确定性必须留在数据里。** 方向缓存曾把"检测全崩"存成"全都不用转"，因为返回值
   把"判定为 0°"和"没有共识"混为一谈。
